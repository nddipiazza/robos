The short version. A per-app VPN sandbox runs one program, such as a browser or a torrent client, inside its own private network room. The only way out of that room is the VPN tunnel. The rest of your computer uses your normal connection as usual. The previous post showed the kill switch: if the VPN connection dies, the app inside the room goes offline. It does not fall back to your real address. That is safe, but it leaves you with a dead app until you pick a new server yourself. And the room only protects a program that was started inside it. If you open qBittorrent from the app grid out of habit, it runs on your normal connection. These two changes close both gaps.

  • Failover means that when the VPN server you picked stops responding, RobOS moves the app to the next server in the list. The app keeps running, and the kill switch stays on during the switch.
  • The App Guard means that once you mark an app as VPN-Only, starting it any other way fails. Any copy found running outside the sandbox is shut down immediately.

You only need the earlier post's background: Linux network namespaces (ip netns), which make the private room, and the three-layer iptables kill switch.

How a down tunnel is detected. Every running session with auto-failover turned on is checked every 10 seconds by runHealthCheckCycle() in packages/robos-lib/vpn-sandbox-engine.js. The check, checkSessionTunnelHealth(), has three steps, from cheapest to most thorough:

  1. Inside the namespace, it confirms that openvpn is still running and that tun0 still has an IPv4 address.
  2. It reads the session's openvpn.log for signs of failure written after the last Initialization Sequence Completed: --ping-restart timeouts, TLS handshake failures, Connection reset, restarting, or a fatal exit. This catches the case where persist-tun keeps tun0 up while the connection behind it is dead.
  3. As the unprivileged app user, it tries a TCP connection to port 443 on three public DNS providers in turn (Cloudflare, Google, Quad9) through the tunnel.

A failed probe only counts once two failures happen in a row. Before blaming the VPN server, the engine checks whether the host has a default route at all. If the laptop itself is offline, the session is reported as host_offline and the kill switch simply stays closed. RobOS does not cycle through servers that cannot be reached anyway. An AUTH_FAILED in the log marks the session auth-error and stops there. Trying other servers will not fix a wrong password, and the unit test checks that exactly one connection attempt is made.

What "next in line" means. getFailoverCandidates() in packages/robos-lib/ovpn-providers.js builds the order. First come the other servers in the same city or name series, starting after the current one and wrapping around. Next come other servers in the same country, then everything else. Profile files are now sorted by number (naturalProfileCompare), so chi-b02 is followed by chi-b03, chi-b04 and chi-b10, then chi-c01, wrapping to chi-b01 before leaving Chicago. Before this change, a plain text sort would put a custom profile named chicago10 before chicago2. The unit test covers both naming styles. A server that fails is skipped for 10 minutes. Each round tries up to 5 candidates. If all of them fail, the session is marked down, the kill switch keeps blocking, and the next health cycle tries again. The Test VPN Connection button uses the same order (testAccountConnection({ autoFailover: true })). It reports which servers it tried and which one answered.

Switching servers without restarting the app. The namespace, its veth pair and the app's process all stay in place. buildSwitchTunnelShellScript() stops only the old OpenVPN daemon (using its pid file, then a pkill inside the namespace) and deletes the stale tun0. It then sets the namespace's INPUT, FORWARD and OUTPUT policies back to DROP for IPv4 and IPv6. It removes the host POSTROUTING MASQUERADE rule for the old server IP, adds the FORWARD and NAT rules for the new server's IP and port, and starts a new openvpn. During the gap, the app can reach only an interface that drops everything. After the new tunnel comes up, the same exit-IP check from the first release runs again. If the namespace's public IP equals your normal IP, the switch is aborted as fatalLeakGate and no other server is tried. The renderer receives each switch as a vpn-failover IPC event, added in packages/vpn-sandbox/main.js along with the Auto-Failover Next Server toggle and the Next Server button.

Layer one: the app will not start outside the sandbox. Locking an app calls installBaseLaunchLock(), which adds up to four gates:

  • Binary gate. With root or passwordless sudo, the real binary is moved aside to <binary>.robos-vpn-real. For files under /usr, /bin or /sbin this uses dpkg-divert, so package upgrades respect the move. A small gate script then takes the binary's place.
  • PATH gate. The same gate script is placed in ~/.local/bin, so the lock also works without root.
  • Desktop launchers. Each matching .desktop file gets a copy in ~/.local/share/applications with NoDisplay=true, and its Exec= points at the gate. This covers the app grid and magnet or .torrent file opens.
  • Autostart. Matching autostart entries are set to Hidden=true.

The gate itself, built by buildBinaryGateScript(), compares readlink /proc/$$/ns/net with the inode of every /run/netns/robos_vpn_* file. If there is no match, it writes a blocked-launch event, shows a desktop notification and exits with status 126 before the real program starts. If there is a match, it runs the real binary with exec. Unlocking restores the moved binary and removes the launcher copies, using the backups in vpn-sandbox-desktop-backups/.

Layer two: copies that slip through are killed. Someone could run the .robos-vpn-real file directly, use an AppImage, or have a copy already running when the lock is added. To catch these, enforceGuardedAppsOnce() scans /proc. For every process that matches a locked app, it reads /proc/<pid>/ns/net. Any process that is not inside a live robos_vpn_* namespace gets SIGKILL, falling back to sudo -n kill -9 if needed. That includes processes in some other namespace, such as a Docker container. A process matches on its executable, its argv[0], an AppImage name, or the script argument when it runs under an interpreter. Some companion binaries are covered automatically: qbittorrent-nox for qBittorrent, and the Qt, CLI and daemon builds for Transmission.

Some processes are deliberately left alone. Wrapper processes such as the host-side sudo ip netns exec robos_vpn_… that launched the sandboxed copy are never matched. Neither are tools like vim, grep, tail or pkill that just have the app's name in their arguments. Core system programs such as bash, sudo, openvpn, ip, node and gnome-shell cannot be locked at all.

Adding a lock runs one scan right away. After that, a systemd --user service keeps scanning even with the window closed. install-vpn-sandbox-guard.sh installs robos-vpn-sandbox-guard.service, which runs vpn-sandbox-guard.js --daemon every 400 ms with Restart=always. The daemon re-reads the guard config only when the file's modification time changes.

What was verified for this post. The 10 tests in packages/robos-lib/ovpn-providers.test.cjs passed:

  • Failover test. Mocked connect and health hooks run the real engine logic. The test launches on chi-b02 while it is "down", lands on chi-b03, then takes chi-b03 down and confirms the health cycle moves the same PID to chi-b04. It also checks that the switch script keeps OUTPUT DROP and swaps the NAT rule to the new server.
  • Guard tests. These run a real gate on a fake qbittorrent (exit 126, real binary never runs) and send real SIGKILLs to throwaway processes. They also confirm that the sandboxed copy, the sudo wrapper and a vim qbittorrent.conf survive.

We also ran the guard's live kernel proof on the dev machine with a separate config folder. It creates a real robos_vpn_g… namespace with a randomly named probe binary, so none of your own apps can match it, and deletes the namespace afterwards.

What was not run here. The live failover proof (proveAutoFailoverOnVpnDrop() in tests/e2e/vpn-sandbox-killswitch-proof.test.cjs) kills OpenVPN inside a real namespace on chi-b02 and expects the app to land on chi-b03. It needs a real VPN account, so it was not run for this post. Without ROBOS_VPN_LIVE_E2E=1, that function returns a canned "simulated-failover-proof" result that does not exercise the tunnel. Treat it as a placeholder, not evidence. The real evidence for failover today is the unit test above.

# Unit tests (failover ordering, launch + mid-session failover, App Guard gate and /proc killer) node --test packages/robos-lib/ovpn-providers.test.cjs # Live 5-phase VPN-Only Guard proof (live-kernel mode needs passwordless sudo; falls back to simulated-guard-proof otherwise) ROBOS_CONFIG_DIR=$(mktemp -d) node packages/vpn-sandbox/bin/vpn-sandbox-guard.js --prove # Lock an app, install the always-on guard service, inspect, unlock node packages/vpn-sandbox/bin/vpn-sandbox-guard.js --lock qbittorrent bash packages/vpn-sandbox/bin/install-vpn-sandbox-guard.sh node packages/vpn-sandbox/bin/vpn-sandbox-guard.js --status node packages/vpn-sandbox/bin/vpn-sandbox-guard.js --unlock qbittorrent # Live kernel kill-switch, auto-failover and guard E2E (uses your saved VPN account) ROBOS_VPN_LIVE_E2E=1 node --test tests/e2e/vpn-sandbox-killswitch-proof.test.cjs # Launch the app from source and capture it scripts/dev-launch.sh vpn-sandbox node packages/robos-lib/snapshot-cli.js vpn-sandbox --screenshot > vpn-sandbox.png
