Guide · for a team

Build apps as a team

A lead turns the goal into tasks. Each developer has an agent implement their tasks and reviews the branch before anyone else sees it. A teammate approves the pull request, and the author merges.

Every step a developer takes on their own task is the same as in the solo guide. This guide covers what changes when several people share one repository and one task tracker.

Who does what

RoleAppsResponsible for
Lead or architectTask PlannerBreaking the goal into small tasks with acceptance criteria, choosing a persona for each, and creating the issues.
Developer (the author)Dev Central, Task Implementer, Agent Code ReviewPicking up a task, running the agent, reviewing its branch, opening the PR, getting CI green and merging.
ReviewerAgent Code Review in reviewer mode, or GitHubReading the diff of a teammate's PR and approving it or requesting changes.

One person can hold more than one role. The rule that matters is that the author is never the only person who reads the change.

Step 1: Set up every machine

RobOS has no shared server for team settings. Each developer's settings live in files on their own machine, so everyone does this once.

  1. Install RobOS and run RobOS Setup Wizard. It sets up pass for tokens, your git identity, SSH keys, gh sign-in and the agent CLIs. See Company setup.
  2. Install and sign in to claude (Task Implementer), the gh copilot extension (Task Planner) and, optionally, codex (walkthrough and evidence in the review window).
  3. In RobOS Task Servers, add the same task server as everyone else:
    • GitHub Issues: the team's repository, using each person's own gh login.
    • Jira: the Jira URL, your username, the project keys, and a pass entry that holds your own API token. Click Test Connection.
  4. Clone the repository. Developers who will run more than one agent at a time need one clone (or git worktree) per running task.

Task Planner and Task Implementer work with GitHub and Jira. The review window, the PR and CI steps work with GitHub, so the code must be on GitHub even when the tasks are in Jira.

Step 2: Share review defaults

Two kinds of settings shape review. Agree on them once, then set them on each machine.

Per repository, in Git Projects

Open RobOS Git Projects, select the repository, and use its review tabs:

  • PR template: Default GitHub PR reviewers (usernames or organization/team, comma-separated) and the PR description template. The reviewers are filled in when an author moves a draft PR to ready, and can be changed per PR.
  • Team messaging: the workspace, channel and notification template for "please review" messages. It needs a workspace configured in Team Chat Servers first; reviewer mentions need Slack.

These are saved under ~/.robos/project-review-settings/ on each machine. They are not synced, so every author sets the same values.

Per team, in the review window

In reviewer mode, Review settings opens the team policy: which review stages are on, which are required gates, the quiz pass mark, the default diff mode and the preferred IDE. It is stored as robos:prReviewTheaterConfig on the team's robos:Team node in the knowledge graph.

Step 3: Plan and hand out the work

The lead does this in Task Planner, exactly as in the solo guide, with a few additions:

  • Put the team's architecture, services and conventions in the planning context. Every task is drafted against it.
  • For Jira, set Parent Epic to attach the tasks to an existing epic.
  • Give each task the persona that matches who, or which kind of agent, should do it: Software Architect, Frontend Web Developer, Backend Systems Developer and so on. On GitHub the persona becomes a role:<persona> label, so developers can filter by it, and Task Implementer picks the persona from it.
  • Make dependencies explicit, so nobody starts a task whose groundwork is not merged yet. On Jira, sync creates Blocks links between dependent tasks, and Task Implementer marks a task whose blockers are still open with a lock and a "Blocked by" warning. GitHub issues are created without links, so name the issues that must merge first in the task body.
  • Keep tasks small enough that one person can review the branch in one sitting.

Then click Sync All to Server. Custom templates and edited personas are saved on the lead's machine (~/.config/robos/task-planner/custom-templates/ and ~/.config/robos/agent-personas.json); copy those files to teammates who should use the same ones.

Step 4: Pick up a task and implement it

Dev Central is where a developer finds work. Its views include Assigned to me, Unassigned and one per workflow stage. Press / to search every task on your task servers, and a to assign the highlighted task to yourself. Assigning first tells the team the task is taken.

Then implement it in Task Implementer, as in the solo guide:

  1. Start Task Implementer from the clone you will work in. The agent works in the folder the app was started from.
  2. Select your task. Check the persona and its Directives, and add context only you know.
  3. Click Start Agent. The agent works on its own branch, codex/<task-key>, so two developers' tasks never share a branch. It commits and pushes, and does not open a PR.

Each agent runs claude with --dangerously-skip-permissions as the developer's own user, with no sandbox. Agree as a team which repositories and machines that is acceptable on.

Step 5: Review your own branch, then open the PR

The author reviews first, before asking anyone else for time. Click Review branch… and follow Step 4 of the solo guide: read the diff, ask the agent for changes, check the evidence and take the walkthrough.

Then open the PR as a draft, so nobody is asked to review until CI is green:

  1. In the Pull Request tab, tick Create as draft and click Create PR. If team messaging is set up, a Send PR review notification option appears.
  2. Watch the CI banner until the checks pass. Get CI back to green can start an agent repair in an isolated checkout; you review and push its fix.
  3. Click Move PR to Ready. The dialog fills Request GitHub reviews from the defaults in Step 2. RobOS checks the head commit, that you are the author, the draft state and CI before it changes anything, and refuses while CI is red.

Step 6: Review a teammate's pull request

The reviewer can review on GitHub as usual, or open the PR in the review window's reviewer mode:

ROBOS_REVIEW_URL=https://github.com/OWNER/REPO/pull/NUMBER \
  ~/robos/scripts/dev-launch.sh pr-review

The legacy Dev Central dashboard (--v1) also has Open code review on each pull request.

  1. Read the Description and the diff on the Changes tab.
  2. In Approve, choose Approve, Request Changes or Submit Comment Only, write your notes and click Submit review. RobOS runs gh pr review. Approving does not merge.

Know what reviewer mode shows today. Description, Changes and Approve use the real pull request. The Overview, Documentation, Open in IDE, Evidence and Walkthrough tabs show built-in sample content, not content from the PR. With the default policy, Changes and Approve stay locked until the sample Overview quiz is passed; clear those locks in Review settings if your team does not want them. Details: PR Review Theater.

When the reviewer requests changes, the author goes back to their local review, asks the agent for the change with Suggest changes, checks it, and pushes the new commits to the same branch. The PR picks them up, and the reviewer looks again.

Step 7: Merge and follow up

The author merges on GitHub once the PR is approved and CI is green. RobOS has no merge button. If CI on main fails after the merge, or the review left work for later, the lead files a follow-up in Task Planner and it goes through the same loop.

Before you roll it out

QuestionAnswer today
Is there a shared server for team settings?No. Task servers, personas, templates and review defaults are files on each machine. Share them by agreeing on values or copying the files.
Which agent implements tasks?Task Implementer runs Claude Code only. Each developer uses their own sign-in.
Are agents sandboxed?Not by Task Implementer. The agent runs as the developer's user without permission prompts.
Does RobOS choose a cheaper model for easy tasks?Not yet. See Agent tiers.
Can reviewers rely on every reviewer-mode tab?Not yet. Use Description, Changes and Approve; the other tabs hold sample content.
