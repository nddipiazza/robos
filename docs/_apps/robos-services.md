RobOS Services installs and manages the servers used by the app suite. Open it from GNOME Applications or the RobOS launcher. Select **This computer** or add a Linux host with **Add SSH host**. Use **Install server** to install the service suite and **Enable boot startup** for Linux user-service lingering.

The suite includes an authenticated gateway, grocery lists, home device/scene definitions, game library and saves, and eLearning courses and progress. Data persists in `~/.config/robos/services/data/`. Every request requires the host's token; **Client connection details** displays it on demand. Remote requests travel through SSH forwarding; APIs listen on loopback.

Select a service to start, stop, restart, enable or disable startup, or read recent logs. Startup settings and running status are separate. Existing `robos-*.service` units are discovered in user and system scopes. System-wide changes require suitable sudo privileges. Windows local hosting uses per-user Task Scheduler jobs at sign-in.

Use **App-owned listeners** or **All services & source inventory** to inspect existing app, Cast, TV, game-control, MCP, socket and debug servers. Source-audited entries do not imply a running process. Embedded listeners stay with their owning app. Linux also discovers listening TCP and Unix sockets in existing RobOS processes; apps loading the shared DOM snapshot library record active Node listeners and endpoints on every platform.

Home Services stores device, scene and automation definitions; physical protocols require separately configured drivers. The game and learning services provide shared storage APIs; existing games and course players need explicit client integrations to synchronize with them. No AI agent is required.

Install from a checkout with `bash packages/robos-services/install-server.sh`, then `bash packages/robos-services/install-desktop.sh` on the GNOME desktop. Agent workflows are available as `install-robos-services` and `manage-robos-services`.

## Client API

Forward the remote gateway with `ssh -N -L 19400:127.0.0.1:19400 USER@HOST`. Include `Authorization: Bearer TOKEN` on all requests, including health checks. Retrieve the token locally through **Client connection details**; do not put it in URLs, source control or logs.

| Service prefix | Collections | Purpose |
| --- | --- | --- |
| `/grocery-lists` | `/lists`, `/lists/{id}/items` | Shared shopping lists and checked items |
| `/home-services` | `/devices`, `/scenes`, `/automations` | Device and automation definitions |
| `/games` | `/library`, `/saves`, `/sessions` | Game metadata, saves and sessions |
| `/elearning` | `/courses`, `/progress` | Course definitions and learner progress |

`GET` reads a collection or an individual resource. `POST` creates a resource with a `name`; `PATCH /{id}` updates it and `DELETE /{id}` removes it. Grocery items accept `quantity` and boolean `checked`. Other resources accept application-specific JSON in `data`; progress records also require `learner`. IDs are generated by the service. Requests are limited to 1 MiB. `/health` checks each service; a stopped upstream returns HTTP 503 through the gateway.

The app and service node registration is prepared in `.robos/proposals/robos-services.json`. Applying it is pending repair of pre-existing aggregate/package disagreement and graph validation failures. The Services nodes validate independently; this change does not rewrite unrelated graph entities.
