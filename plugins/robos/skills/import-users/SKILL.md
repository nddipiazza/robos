# Import users and groups

Use Graph Explorer → Populate RobOS apps → Users → Groups → Review import. Dogfood this workflow when it is available; do not write canonical graph files or People Directory records directly. The implementation is `packages/robos-graph/lib/identity-import.js` and `app-configuration-import.js`.

1. Open the explicit company graph workspace. Read `import-company-kgraph` for graph proposal/evidence rules. Preserve existing connections; deselect task and pipeline servers when importing identities only.
2. Establish the email domains to include, for example `@example.com, @subsidiary.com`. The Users step supports a comma/newline-separated allowlist, case-insensitive exact matches. Blank means all domains; subdomains are not implicitly included. Never broaden the allowlist silently to recover personal accounts. Ask how confirmed people with only personal Git identities should be handled. An email domain alone does not prove current employment.
3. Discover from explicit local Git checkout paths. RobOS reads `git log --all --format=%H%x09%aN%x09%aE`, respects mailmap author identities, deduplicates checkout origins, combines aliases by email, excludes bots, and records repository/commit evidence. Fork history contains upstream authors; never import all historical contributors as employees. Separate emails remain separate candidates until evidence establishes their identity; do not merge names alone.
4. Optionally enter Google Cloud project IDs. RobOS reads `gcloud projects get-iam-policy PROJECT --format=json` using the signed-in CLI. Import human `user:` principals as candidates. `group:` principals reveal addresses, not membership. Never infer job titles from IAM roles, import service accounts as people, change IAM, or expose tokens. Report access failures without inventing missing identities. Cloud Identity membership APIs may be used read-only when explicitly authorized and available; preserve evidence and distinguish direct from transitive members.
5. Use **Add a confirmed person** when the user supplies a company identity absent from source discovery. Enter the confirmed full name and email; RobOS normalizes email case, enforces the same domain filter, and records the assertion as user-confirmed evidence. Do not invent an address from a naming convention. Select current team members and correct display names in Users. Keep excluded, ambiguous, and historical identities unselected. Changing discovery inputs invalidates old selections and requires discovery again. Review source evidence per row.
6. In Groups enter the user's membership instructions in the supported form, one group per line: `Developers: person@example.com, another@example.com`. Names work only when unambiguous. Only selected users may be members. Do not guess memberships from contribution counts or repository permissions. Existing same-name groups receive exactly the reviewed membership list; unrelated groups remain intact.
7. Inspect Review import: people, emails, each group's membership, and other selected app changes. Apply the reviewed proposal through the wizard within the user's authorized scope. Re-preview if graph, settings, or local people/groups changed. Canonical graph writes must go through GraphWorkspace validation and proposal application. Import receipts are stored under `~/.config/robos/import-receipts` and identify staged files if an interrupted import needs reconciliation.
8. Verify the resulting Person/Team nodes and membership references through Graph Explorer and the records through People Directory / Group Manager. Capture live wizard proof and report actual imported counts, excluded candidates, unresolved identities, and access limitations. Discovery alone is not a completed import.

No messages, invitations, task assignments, or IAM changes are part of this import.
