What this is. Most of us have an old phone in a drawer. RobOS Assistant for Android turns one into a room assistant you can leave on a kitchen counter or mount on a wall. It listens all the time, the way a security camera watches all the time: each time someone speaks, it saves the audio clip and a text transcript on the phone. When you start a sentence with "Commander," and the phone can reach your RobOS computer, that sentence becomes a command: "Commander, we're out of eggs" adds eggs to the grocery list, and the phone answers out loud.

Why someone would care. Commercial smart speakers send your voice to a company's cloud. This setup never leaves your home network: the phone talks only to a RobOS computer on your Wi-Fi (we call it the RobOS Server), which runs open-source speech models locally. It works on the RobOS phone image with no Google Play Services, and the app now ships inside that image. It also borrows the always-on design of RobOS IP Camera for Android, so the screen can be off, locked or blacked out and it keeps listening.

Prerequisites, if you want to follow along: an Android 11 or newer phone, a Linux machine running RobOS with Node.js, and both on the same Wi-Fi. Everything below happened over one evening, on November 23, 2026, in six commits.

What you can say, and what it ignores

The rule ended up simple: "Commander" has to be the first word, and a real command has to follow it in the same breath. Everything else in the room is recorded, but nothing happens. We checked this against the real server code while writing this post, using a test server with a throwaway shopping list:

1. The phone: always recording, never acting on its own

The Android app (packages/robos-assistant-android, commit 96c9168b) is about 6,000 lines of Kotlin with four tabs: Listen (live waveform and transcript), Recordings (searchable archive), Assistant (wake phrase, voice and storage settings) and Server (connect to RobOS).

  • It keeps listening with the screen off. Capture runs in an Android foreground service of type microphone that holds a CPU wake lock and a low-latency Wi-Fi lock, and restarts after a reboot (AssistantServerService.kt, MicrophoneEngine.kt).
  • It cuts speech into sentences. A voice activity detector watches loudness, keeps a short "pre-roll" buffer so the first syllable is not lost, and closes an utterance after a stretch of silence (AdaptiveVadSegmenter in AudioSurveillancePipeline.kt).
  • Every utterance is saved twice: a .wav clip and text. Storage is capped (by default 500 clips or 512 MB, oldest deleted first) in Model.kt.
  • No server, no actions. When the RobOS Server is unreachable the app shows Recorder Mode Only, transcribes on the phone with the offline Vosk model (vosk-model-small-en-us-0.15, OfflineVoskEngine.kt) and labels even a "Commander, ..." sentence as Server Offline, Recorded Only. The unit test disconnectedFromRobosServerRecordsAudioAndTextWithoutRunningActions pins this down.
  • It does not hear itself. While the phone plays a reply, microphone input is thrown away, with a short cooldown afterwards, and a transcript that repeats the start of the last spoken reply is dropped.
  • A small web console on the LAN. The phone serves a browser page on port 8090 with a live audio stream (/audio.wav), live transcripts (/api/stream) and clip playback (/recordings/<id>.wav), with optional HTTP Basic auth whose password is stored with the Android Keystore (HttpAssistantServer.kt).

A note on privacy, since this is a microphone that never turns off: recordings stay on the phone, the console is reachable only on your own network, and the clip and size limits stop it from growing without bound. It is meant for your own home.

2. The server: one always-on service the phones talk to

The phone needs something to talk to. The existing RobOS Voice app (packages/voice-prompt/main.js) gained a few HTTP endpoints for phones on port 19188:

  • GET /api/robos-assistant-hub: the phone's "are you there?" probe. It also registers the phone (name, room) so the server knows who is connected. GET /api/assistant-nodes lists phones seen in the last minute.
  • POST /api/assistant/phone-turn: run a typed request from the phone's Ask RobOS box and return the reply as text and audio.
  • POST /api/assistant/process-audio: the main path, added in the next commit. The phone uploads an utterance and gets back the transcript, whether it was a command, what happened, and a spoken reply.

To find the server, the phone first retries the last address that worked, then probes every address on its Wi-Fi subnet, 40 at a time with a short timeout, and keeps the first one that answers (discoverServerHostIp in RobosVoiceServerClient.kt). No cloud relay is involved.

For the server to be there whenever someone speaks, it has to survive logouts and reboots. Commit 1f59ced2 added install-voice-server.sh, which writes a robos-voice-server.service systemd user unit (Restart=always, NoNewPrivileges=true, PrivateTmp=true), turns on lingering so it runs without anyone logged in, and starts the server headless. You can also run it in the foreground with robos-voice serve and list connected phones with robos-voice assistants (packages/robos-cli/robos-voice).

3. Speech recognition moves to the server: Whisper first, then Moonshine

Vosk on a phone is small and works offline, but it makes mistakes, and a misheard word in a command means the wrong thing gets added to a list. A RobOS desktop has far more computing power than an old phone, so commit 332ca165 made the phone send each utterance's .wav to the server whenever it is connected. The server transcribes it with OpenAI's open-source Whisper model (whisper-base.en, with whisper-tiny.en as a fallback) in whisper-worker.js, then checks for the wake phrase and runs the command. The same commit renamed the wake word from "Hey Nabu" / "RobOS" to "Commander", everywhere RobOS listens: the desktop app, the Home Speaker router, the dashboards and the skills.

Whisper was accurate, but it pads every clip to 30 seconds of audio before decoding, so a two-word command cost as much work as a long sentence. An hour later commit 42d296ec put a faster model in front of it. stt-engine.js now trims leading and trailing silence and decodes with Moonshine, a speech model built for short phrases, running as 8-bit (INT8) ONNX through the sherpa-onnx C++ runtime. If Moonshine is not installed, it falls back to Whisper, so the title of this post is still true on a fresh machine.

4. Making it fast, then backing off a little

A voice assistant that takes several seconds to answer feels broken. Commit 42d296ec went after every delay it could find:

  • Smaller audio chunks on the phone. The microphone thread now reads 30 ms frames instead of about 160 ms, at Android's URGENT_AUDIO thread priority.
  • Less waiting for you to finish. The silence that ends a sentence dropped from 1,100 ms to 420 ms.
  • A voice that is already warm. Instead of starting the Piper text-to-speech program for every reply, tts-engine.js keeps one Piper process running and feeds it requests line by line (--json-input). The installer loads both models as soon as the service starts, so the first request of the day is not slow.
  • No desktop lookups on a headless server. context-provider.js stops asking the window manager which app is open when there is no desktop.

The commit message records about 180 to 250 ms for server speech recognition and about 190 ms for a fresh spoken reply, roughly ten times faster than before. Those are the author's measurements on the RobOS Server. We did not re-measure them for this post: the laptop used to write it has no Moonshine install and only the slower Python build of Piper.

Two parts of that speed push did not last. The commit also added a "reflex": a tiny on-phone recognizer listening only for "Commander", which immediately played a cached "Yes, Commander?" and waited for the command. Three hours later it was removed (next section). And the 420 ms silence cutoff turned out to be too eager: people pause after "Commander," and the sentence got split in two. A later commit, 5ab95bbe, raised it to 1,050 ms and moves existing phones over automatically.

5. Teaching it to ignore the TV

Leaving a room microphone running all evening showed the problem fast: "commander" is a common word. It turns up in conversation, in TV shows, in games, and in the name of a popular card-game format. Commit f5d0c84e made three changes, matching on both the phone (WakeWordParser) and the server (wake-word.js):

  • "Commander" must start the sentence. The pattern is anchored to the start, allowing only a filler word in front ("and", "um", "uh", "so", "well", "oh") and an optional greeting such as "hey" or "ok". "I built a new Commander deck yesterday" no longer matches.
  • "Commander" on its own does nothing. The "Yes, Commander?" reply, the follow-up listening window and the on-phone wake spotter were all removed. One sentence, one command.
  • Fixes for how real rooms sound. Speech recognition heard "add" as "at" ("Commander at garbage bags to the Costco shopping list") and "grocery list" as "grocery label"; both are now understood. A bare "Commander, undo" works. And an open question such as "Commander, what kind of things can I do..." can no longer be added to the list as if it were an item.
// packages/voice-prompt/lib/wake-word.js (after f5d0c84e)
const WAKE_PATTERNS = [
  /^(?:(?:and|um|uh|so|well|oh)[,.\s]+)?(?:hello|hey|hi|ok|okay|yo)[,\s.-]*commander\b/i,
  /^(?:(?:and|um|uh|so|well|oh)[,.\s]+)?commander\b/i,
];

6. The first real job: the grocery list

The household Shopping Lists (see the earlier Android PWA and voice sync post) already understood "add milk to grocery". Commit f08c3aae taught it to understand how people actually talk in a kitchen (text-commands.js, defaults.js):

  • You don't have to say "grocery list". A shared check, isLikelyShoppingVoiceCommand, recognizes "we're out of eggs", "running low on olive oil" and "do we need avocados?" as shopping requests, while leaving "add a task to fix login" alone.
  • Questions are answered, not added. "Is milk on my grocery list?" looks the item up, including on the other stores' lists and in the cart, instead of adding "is milk".
  • Reading the list back by aisle. "What do we need in Produce?", "What's in my cart?", "How much is my Costco list?", and filters for urgent, organic or deal items.
  • Twelve meal and household bundles that work offline: taco night, pasta night, breakfast, burger night, pizza night, smoothies, stir fry, salad, lunchbox, baking, party snacks and a sick-day kit, plus one-command store staples.
  • Editing by voice: check off several items at once, "double the avocados", notes, prices, moving an item to another store, clearing a list, creating a new store list, and a spoken cheat sheet ("Commander, what can I say for grocery lists?"). The printable guide in PRINTABLE-GUIDE.md lists every phrase.

One thing we noticed while testing for this post: "Commander, undo" reverses removals and clears, but not additions. Saying it right after "add taco night" answers "No command undo." because adding items does not record an undo step in store.js.
