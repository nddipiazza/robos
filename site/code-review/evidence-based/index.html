Evidence-Based Code Review

Reading every line of every pull request was never what kept an app stable. Tests, contracts and fast rollback did that. This page shows how to move a reviewer's judgment to the start of the work, where it becomes executable, so that people can stop reading getters and setters and still sleep at night.

The short version. Tech leads and reviewers write the assertions and test scenarios while the work is planned. The agent writes the code against those scenarios, with the project's context in front of it. A change merges when there is evidence, captured on that exact commit, that every scenario holds and nothing else broke. A person still reviews the change, but conceptually: what moved, which modules, why, and whether the tests ask the right questions. Nobody comments on tabs.

Why line-by-line review stopped paying

The classic pull request review asks one or two people to read a diff and find what is wrong with it. In practice that process is:

  • Slow. Most of a PR's life is spent waiting in a queue for a reviewer, not being reviewed. Every round of comments restarts the wait.
  • Subjective. A large share of comments are about naming, formatting, ordering and personal taste. They create rework and arguments, and almost none of them change what the software does.
  • Shallow on the changes that matter. Attention drops as diffs grow. A 30-line change gets ten comments; a 1,500-line change gets “LGTM”. The biggest, riskiest changes get the least real review.
  • Rarely the thing that catches the bug. Now and then a reviewer finds something valid, and that occasional find is used to justify the whole ritual. Most defects that reach production were in code somebody approved.
  • Outrun by agents. An agent can produce more correct-looking code in an hour than a person can carefully read in a day. If every line still needs human eyes, the reviewer becomes the bottleneck of the whole team, or starts rubber-stamping.

None of this means people are bad at reviewing. It means they were given the wrong job. People are good at judging intent, design and risk, and bad at exhaustively checking hundreds of lines for mistakes. Machines are the opposite. Evidence-based review gives each side the job it is good at.

The shift: reviewers write assertions, not comments

In the old process, a senior engineer's knowledge reached the code as review comments, after the code was written, one PR at a time, and was lost when the PR merged. In the new process, the same knowledge is written down before any code exists, as tests that every future change must pass, and as context every future agent reads.

  1. PlanEpics and tasks with acceptance criteria. Leads and reviewers write the scenarios as tests.human
  2. Approve the scenariosThis is where the review rigor goes. Small, readable, argued over.human
  3. ImplementThe agent works from the task, the scenarios and the project's context, and makes the tests pass without editing them.agent
  4. ProveTests, before-and-after evidence, walkthrough, impact check, CI. All bound to the commit.machine
  5. Concept reviewMinutes, not hours: what changed, which modules, do the tests still ask the right questions.human
  6. Deploy on evidenceStaged rollout, health checks, automatic rollback. Escapes become new scenarios.machine

The total amount of human judgment doesn't go down. It moves to the steps where it is cheapest and most reusable. A scenario written once protects every later change to that feature. A review comment protects one PR.

Context engineering: decide what the agent knows before it writes

“Context engineering” means treating everything an agent reads before and during a task as a designed part of the system, versioned and reviewed like code. The more the agent knows about your conventions, architecture and expectations, the less its diff surprises anyone, and the less there is for a person to catch. In RobOS, the context comes in layers:

LayerWhere it livesWhat it prevents
Project conventionsAGENTS.md at the repository root (with CLAUDE.md and GEMINI.md pointing to it)Style comments, “we don't do it that way here”, wrong test framework, wrong folder
Repeatable proceduresSkills, such as create-test, e2e-driven-dev and plan-before-implementGuessed selectors, missing tests, skipped verification steps
Architecture and dependenciesThe knowledge graph; kgraph-impact-analysis lists who depends on what you change“I didn't know the billing service called this”
The task itselfThe issue from Task Planner: scope, acceptance criteria, happy-path, negative and edge casesBuilding the wrong thing, or half of it
The roleThe task's developer persona (Software Architect, Backend Systems Developer, …)A backend task done with front-end habits, and the reverse
The contractThe scenario tests (next section), which the agent must make pass and may not editCode that passes because the test was weakened

The rule that makes this a process rather than a pile of documents: when a review finds something, fix the context, not just the code. If a reviewer has to say the same thing twice, it belongs in AGENTS.md, a skill, a lint rule or a scenario, so that no reviewer ever has to say it again.

The test scenario repository

The scenario repository is where the team's expectations of the software are written as executable tests. It can be a folder in the app's repository (simplest: scenarios/) or a separate repository shared by several services. Three rules make it work:

  1. Scenarios are written in planning, before implementation. The tech lead or the reviewers who would have reviewed the PR write them, from the task's acceptance criteria. They start out failing, which is the point.
  2. Scenarios are owned by people, not agents. Code owners on the folder mean any change to a scenario needs a lead's approval. An agent may add scenarios; it may not edit or delete one to make its code pass.
  3. Scenarios assert exact outcomes. “The page loads” proves nothing. “Choosing Cats shows exactly Mochi and Pepper” does.

What a scenario looks like

Using the same sample project as the Code Review Theater guide: issue #42 asks Pawfinder for a species filter and better ranking. Before anyone implements it, the tech lead writes this file and gets it approved:

// scenarios/search/species-filter.test.js
// Issue #42 · written in planning · owned by @acme-corp/tech-leads
// Agents: make these pass. Do not edit or delete them; add new tests in a new file.
const test = require('node:test');
const assert = require('node:assert/strict');
const { search } = require('../../src/pets');
const { get } = require('../helpers/http');

const names = (pets) => pets.map((p) => p.name);

test('a species filter returns only that species', () => {
  assert.deepEqual(names(search({ species: 'cat' })), ['Mochi', 'Pepper']);
});

test('species and text search combine', () => {
  assert.deepEqual(names(search({ species: 'rabbit', q: 'a' })), ['Waffles']);
});

test('prefix matches rank before matches inside a word', () => {
  assert.deepEqual(names(search({ q: 'b' })), ['Biscuit', 'Juniper', 'Scout', 'Pepper']);
});

test('an unknown species is rejected and lists the valid ones', async () => {
  const res = await get('/api/pets?species=dragon');
  assert.equal(res.status, 400);
  assert.deepEqual(res.body.valid, ['cat', 'dog', 'rabbit']);
});

// Regression guard: callers that never send a species see today's behavior.
test('no species keeps every pet', () => {
  assert.equal(search({}).length, 6);
});

Reviewing these 30 lines carefully is a better use of a senior engineer's time than reading the 300 lines of implementation that will make them pass. They say exactly what “done” means, they include the negative case and the regression guard, and they keep protecting the feature after the PR is long merged.

Behavior that only shows up in the running app gets the same treatment in the walkthrough format, which the agent runs and you watch:

{ "title": "Filter by species in the UI",
  "given": "The app is running with the sample pets.",
  "when":  "Choose Cats, then type pep in the search box.",
  "then":  "Exactly Mochi and Pepper show after choosing Cats; only Pepper after typing pep." }

Strong and weak assertions

Weak (proves little)Strong (fails when it should)
The search endpoint returns 200Searching for cat returns exactly Mochi and Pepper, in that order
An error is shown for bad inputspecies=dragon returns 400 with valid: ["cat","dog","rabbit"]
The list is sortedFor “b”, prefix matches come before matches inside a word, with the expected order spelled out

Nothing about what must stay the sameRegression guards: existing callers, response shapes and limits that must not change

Non-functional expectations belong here too, where you can measure them: a latency budget for the search endpoint, a maximum bundle size, “this page makes no more than two API calls”, “this migration runs in under a minute on a copy of production-sized data”.

Wire it into the agent's context

RobOS doesn't read a scenarios/ folder on its own. A few lines of context tie it in. In AGENTS.md:

## Scenarios
- Tests under scenarios/ are written by tech leads during planning. They define "done".
- Make the scenarios named in the task pass. Never edit, skip, or delete a file under
  scenarios/ or weaken an assertion in test/. If one looks wrong, stop and say why.
- New cases go in a new file. Capture before-and-after evidence for every scenario
  named in the task, on the final commit.

In each task (Task Planner's acceptance criteria are the natural place), name the scenario files that define it. Then protect them with code owners so the rule is enforced by GitHub, not by trust:

# .github/CODEOWNERS
/scenarios/      @acme-corp/tech-leads
/test/           @acme-corp/tech-leads
/src/auth/       @acme-corp/security
/migrations/     @acme-corp/data-owners

Evidence gates: what has to be true to merge and deploy

“Evidence-based” means a change is allowed forward because of things that can be checked, not because someone felt good about it. Each gate below produces a record. If a record is missing, stale or failing, the change stops.

GateThe evidenceProduced byIn RobOS today
Scenarios passThe task's scenario tests, green, unmodifiedThe test runner in CIYour CI; the agent runs them before it commits
Behavior is visibleBefore-and-after captures of each scenario, from main and the branchThe agent, in a real browser or containerEvidence tab, with templates for UI, command output, MCP/API and task checks
Evidence is currentEvery capture records the commit and a checksumRobOSStale evidence is marked and refused when the PR is created or moved to ready
Someone saw it workWalkthrough checkpoints, each observed in the running appThe agent drives, a person watchesWalkthrough tab; an unverifiable checkpoint is recorded as unverified
Blast radius is knownThe list of modules and services that depend on what changedThe knowledge graphkgraph-cli.js impact (the kgraph-impact-analysis skill)
Nothing else brokeFull test suite, lint, type check, secret scan, dependency auditCIYour CI; the PR tab shows its state and Get CI back to green
Required steps are doneChanges viewed / evidence fresh / walkthrough finished, as the repository requiresRobOSReview steps: Required, Optional or Hidden per repository
It holds in productionHealth checks and error rates during a staged rollout, with automatic rollbackYour deploy platformNot in RobOS. Deploy Tracker shows deployments and merged PRs but has no rollout or rollback controls

The last row is what makes it safe to review less up front. A change that ships behind a feature flag to a small slice of traffic, with error rates watched and rollback automatic, has a much smaller worst case than a change someone read carefully and shipped to everyone at once. If you skip line review, don't skip this.

What the human still reviews

The review doesn't go away. It changes focus from the characters on the screen to the change as an idea. The goal is that, after a review, you understand the system well enough to explain the change to someone else, and to debug it at 2 a.m. if you had to.

Read carefully

  • Changes to scenarios and tests, line by line. A weakened assertion is the most dangerous line in any diff.
  • Code on risky surfaces: authentication and permissions, money, deleting or migrating data, concurrency, public APIs and contracts, secrets, infrastructure and deploy config.
  • New dependencies: what they are, who maintains them, what they can reach.
  • The evidence: does each capture show what its scenario says?

Skim for shape

  • Which modules changed, and whether that's where this logic belongs.
  • New boundaries: new files, classes, services, endpoints, tables.
  • Data flow: where input enters, where it's stored, where it leaves.
  • Anything the blast-radius check says depends on the changed code.

Skip

  • Getters, setters, boilerplate and generated code.
  • Formatting, whitespace, tabs versus spaces, import order. The formatter owns these.
  • Naming preferences that aren't actually misleading.
  • Re-checking what a passing scenario already proves.

If a skipped item really bothers you, don't leave a comment. Encode it once: a lint rule, a formatter setting, a line in AGENTS.md. Then it's enforced on every change, by a machine, without a debate.

Learn the change, not the lines

The Code Review Theater is built for this kind of review. A good order:

  1. Description and walkthrough checkpoint 1 (Understand the change): the agent summarizes the diff by module and says what to try. Ask it questions until you could explain the change yourself.
  2. Evidence: look at every before-and-after pair. This is the part users will see.
  3. Changes: open the test and scenario files first and read them fully. Then go module by module through the rest, reading the risky files and skimming the others. Mark files Viewed as you go; Hide viewed keeps the rest in front of you.
  4. Walkthrough: watch the agent use the change in the running app, and try it yourself.
  5. Ask, don't comment. If something should be different, ask the agent in the chat; it edits, tests, commits and regenerates the evidence.

Change size: small by default, big when it's coherent

Keep changes reasonably small. Small changes have small blast radii, fast evidence runs and easy rollbacks. But don't treat a line count as a rule. With scenarios carrying the correctness load, a big change is fine when it's one coherent idea:

Big and fineBig and worth splitting
A mechanical change across many files: a rename, a new required argument, an API version bump at every call siteA refactor mixed with a behavior change: split them, so the refactor can be proven to change nothing
Generated code, lockfiles, migrations produced by a toolTwo unrelated features on one branch
A new feature that only makes sense whole, fully covered by its scenariosA change touching several risky surfaces at once (auth and billing and a migration)
Deleting dead codeA change whose scenarios don't cover most of what it touches

Ask for a split when concerns are mixed, not when the number is large. For a big but coherent change, review by module map: let the agent explain it module by module, read the scenarios and the risky files, and let the evidence carry the rest.

When it's safe to opt out of line review

Opting out isn't all or nothing. Decide by risk, and make the decision visible in the repository's review settings rather than in each reviewer's mood.

Set the repository's default tier in Git Projects › PR review › Review steps. For one review, a launch manifest can raise it, for example "reviewSteps": { "changes": "required" }. RobOS sets steps per repository and per review; it doesn't pick a tier from the changed paths by itself, so code owners on the risky folders are what force the line review there. Keeping high-risk code in its own repository, with its own stricter defaults, also works.

Tripwires: what pulls a change back into line review

Whatever the tier, any of these means a person reads the relevant lines:

  • A file under scenarios/ or test/ was edited or deleted, a test was skipped, or the number of assertions went down.
  • Coverage of the changed lines is low, or a changed module has no scenario at all.
  • Evidence is stale, a scenario is blocked, or a walkthrough checkpoint was continued as unverified.
  • The change touches a code-owned risky path, adds a dependency, or changes a public contract.
  • The blast-radius check shows dependents nobody expected.
  • The agent said it was unsure, or worked around something instead of fixing it.

The first one is cheap to automate in CI. A sketch to adapt:

changed=$(git diff --name-only origin/main...HEAD)
if echo "$changed" | grep -qE '^(scenarios|test)/'; then
  echo "Tests or scenarios changed: a code owner must read them line by line."
  # Fail outright if a test or assertion line was removed.
  git diff origin/main...HEAD -- scenarios test | grep -E '^-\s*(test|it|assert)' && exit 1
fi

Prove it isn't hurting stability

“We stopped reading every line” is a claim. Back it with numbers you track before and after the switch:

MetricWhat it tells you
Change failure rateShare of deploys that cause an incident or rollback. It should not go up.
Time to restoreHow fast a bad change is undone. Staged rollouts should bring it down.
Escaped defects, by areaBugs found in production, grouped by feature. An area that keeps leaking needs better scenarios.
Review lead timeFrom “ready for review” to merged. This is what you gain.
Scenario coverageShare of tasks that named scenarios before implementation started.

When something escapes, the fix is never “review harder”. Write the scenario that would have caught it, add it to the scenario repository, and, if the agent lacked something it needed to know, add that to the context. Each escape makes every future change safer. That loop, more than any single review, is what keeps the app stable.

Roll it out in four steps

  1. Plan with scenarios. In Task Planner, keep the acceptance criteria and test cases on every task, and have the lead turn them into scenario files before the task is picked up. Add the scenario rules to AGENTS.md and code owners on scenarios/.
  2. Implement against them. Task Implementer hands the issue, with its scenarios and persona, to the agent. The e2e-driven-dev skill follows the same order: failing test first, then code.
  3. Require evidence, not reading. In Git Projects, set the repository's review steps to the tier that fits it. Start with Normal on one repository with good tests.
  4. Measure, then widen. Watch change failure rate and escapes for a few weeks. Turn every escape into a scenario. Move more repositories over as the numbers hold.

What this doesn't solve

  • Scenarios only test what someone thought of. That's why the concept review, the blast-radius check and the staged rollout stay. They catch what nobody wrote down.
  • Specialist review still matters. Security-sensitive code and anything with legal or regulatory weight keeps a qualified person reading it. If your compliance rules require two-person review of every change, this process reduces what that review has to cover; it doesn't replace it.
  • Evidence uses sample data. Before-and-after captures prove behavior on the data in the test environment, not on production data. Each evidence bundle lists what remains unverified.
  • Reviewer mode doesn't read the author's evidence yet. In the Code Review Theater today, the evidence and walkthrough are the author's, in their local review. Link the evidence in the PR description (Edit with agent embeds the screenshots) until reviewer mode reads it; see Reviewer mode.
  • Production gates are yours to build. RobOS has no rollout or rollback controls. Use your deploy platform's feature flags, canaries and health checks.
